# 资料库维护指南

## 维护目标与文件分工

本库以社区内容汇总与经验分享为目的，尊重原作者在模型、工具、教程和示范作品上的投入。维护质量看“能否找到原文、准确理解作者分享，并在相应版本下参考”，不以链接数量或每日条数衡量。

| 文件 | 保存什么 | 何时改 |
|---|---|---|
| `README.md` | 项目用途、阅读入口、来源范围与使用方法 | 用途、结构或入口变化时 |
| `每日检索可速查总结.md` | 日期目录、主题与资源入口、待补缺和待验证项 | 日报归档、结论更正或资源实质变化时 |
| `daily/YYYY-MM-DD.md` | 当日问题、原始证据、同图配方、对照、方法与限制 | 当日执行、同日重跑及必要更正时；首次归档后产生目录 |
| `docs/检索规范与日报模板.md` | 固定来源、收录与证据规则、日报格式 | 用户范围或记录规则改变时 |
| `docs/每日生图搜索流程规划.md` | 从问题、搜索到示范学习和迁移的执行顺序 | 搜索与学习方法改变时 |
| `skills/image-workflow-research/` | 用户提供的通用技能和两份 references | 有明确技能修订需要时；不为一次个图参数改动 |
| `AGENTS.md` | 自动化与后续助手的维护入口和核心约束 | 维护入口或长期约束改变时 |

具体模型、词串、数值和反馈留在有版本的日报／案例中；通用文档只提炼选择、调整与判断方法。README 和索引链接到正文，不复制整套检索规则。

## 署名、原文链接与整理用语

- 将社区成果归于原作者，使用“原作者分享”“据原教程介绍”“社区使用反馈”“本库整理备注”等表述。方法归纳与对照注明借鉴来源，保留读者回到原文的入口。
- 每条收录资料附原作者、原帖标题、平台、日期和原文直达链接。经转载发现时追溯原作者，同时保留确有帮助的发现入口；未能确认原作者时写待核实，不将转载者误作原创者。
- 区分原文引用／转载摘录、本库概述、本库学习对照与后续实际实验。引用保留原意，补充说明标清归属；翻译或改编注明原文与改动。
- 摘录和整理引导读者阅读原教程，引用、转载与素材使用遵循原作者说明及适用许可。署名和链接不作为取得转载授权的证明，第三方成果不归入本库原创。
- 讨论适用性时具体说明版本、输入条件与本次观察，尊重作者经验；本库尚未复核的内容如实标记，不用贬低或居高临下的措辞评价社区分享。
- 原作者提出署名、纠错或收录调整时，记录并按具体请求处理，同步正文和索引。

## 每次维护的顺序

1. 读取仓库最新版本、`AGENTS.md`、本指南及相关规范；检查待处理问题和已有条目。以用户最新要求为准。
2. 判断是新增来源、同资源新版本、补齐配方、修正结论，还是仅转载；确定应更新的已有文件。
3. 先写完整日报或更新相应正文，保留原教程帖、版本、证据状态、缺口与适用范围。
4. 再更新总索引，让日期入口、主题入口及待验证项指向实际存在的正文。首次成功日报写入后，移除索引中的“待首次执行”和相应占位行。
5. 涉及长期范围或方法变化，同步规范与流程；涉及归档路径或任务实际输入变化，同步现有定时任务的提示。不能只改说明就宣称自动化已经生效。
6. 根据实际保存结果反馈：报告修改内容、关键文档链接和仍待解决的问题。没有成功写入的内容明确标为未归档。

同日重跑更新 `daily/YYYY-MM-DD.md`，用简短记录说明补充或修正，不重复建第二份日报。跨日补充旧资料保留真实发布日期，明确历史补录或更正时间。

## 收录与去重技巧

- 以“规范原始 URL＋精确版本／revision＋具体示范图或配方”识别条目。资源标题、文件名与转载标题都不单独作为身份。
- 一个资源多处转载合并到同一条记录；发现入口可保留，结论尽量回链原作者教程。
- 同一模型的不同版本、预测类型或作者配方分开，说明差异；相同版本有实质更正时补充既有记录。
- 再次报道要写“相比上次改变了什么”，并链接旧条目。仅发布时间重置、转载或热度变化不算配方更新。
- 视觉接近但资料不全的示范进入待补件清单；完整但不适合目标的资料可说明用途，不抢占优先推荐。
- 原教程没有给出的信息写未知，不为了表格完整而补造参数；原图配置、作者通用建议与工程拟补值分列。

## 让资料容易查到

总索引同时提供日期入口与主题入口。主题宜沿用“后训练模型、LoRA 与画师混合、工作流与结构控制、提示词与质量优化”，在条目中补充实际问题词，例如线条、服装保持、双人、光影。

每条索引保留资源／精确版本、用途、最近收录日期与日报章节入口。首次收录时选择不会频繁改名的标题；更名时同步引用。记录常用中英文名与别名，以免 stable diffusion／stablediffusion 或光辉／Illustrious 被当作不同来源。

长提示词与完整配置保留在对应日报附录，通过摘要链接查阅。一个文件仍易查时不拆分；确实需要独立案例时，将相关配方、执行记录与反馈放到同一案例位置并建立回链。

待处理项写清“缺什么、为什么影响判断、下一步去哪找”，避免只写“以后研究”。解决后记录日期及证据入口，再从当前待办中移出，历史说明保留。

## 证据状态与结论更正

分别记录资料取得、执行状态和评价范围，不能将它们合成一个“验证通过”：

- 资料：摘要／简介、已读正文、视频或评论读取范围、完整工作流、原生例图及元数据等。
- 执行：仅读取、缺件待补、原配方复跑、偏离复现、仅采用局部建议；无记录即未执行／未取得。
- 评价：原作者说明／社区报告、机制假设、本地观察、用户明确认可，分别标明对象与适用范围。

保存文档不代表生成器已实现。加载或编译成功不代表画质成立；一次成功不扩展为跨人物、景别、种子和主体数量的稳定结论。

发现错误时，在原条目旁标注“更正日期、原判断、修正内容与依据”，同时更新索引摘要和相关待验证项。涉及私密信息等需要移除的内容按实际要求处理，不为保留历史继续暴露。

## 失效链接、旧版本与相反证据

- 当天实际使用的关键链接，记录最后读取日期与状态。失效标为“暂不可读／已删除／需登录／原因未知”，按真实情况填写，不把访问失败当作教程无效。
- 优先寻找同作者模型卡、仓库、Release、视频说明或可信公开存档，原帖地址与替代来源都保留，注明各自证据范围。搜索摘要不能冒充全文。
- 资源升级后，旧配方仍保留版本条件；不将老教程参数直接提升为新版默认。需要重新核对时加入待复核。
- 相反结论一并记录，比较版本、前端、输入方式和生效分支。将冲突写清，不能只留下支持当前方案的来源。
- 不将临时下载地址、签名地址或登录态链接作为唯一引用。避免记录 token、账户凭据、私人会话或无关个人资料。

建议每积累约 7 份日报进行一次简短整理：合并重复、核对高价值索引和失效链接、关闭已解决待办、检查规则与现有任务是否一致。可随一次正常维护完成，无需另建定时任务；未实际完成不记为已完成。

## 文件与提交技巧

- 使用 UTF-8 Markdown；日期与检索时间使用北京时间。优先相对路径连接仓库内资料，外部资料使用原帖直达链接。
- 只按必要范围保存小型配置与已授权素材；大模型、运行环境、缓存和临时输出不入库。工作流与图片仍保留原作者来源及已知使用条件，不擅自给第三方内容声明授权。
- 修改前读取当前内容与 SHA，保留并发新增内容。写入冲突时重新读取、合并再保存，不覆盖远端。
- 提交说明指出具体变化，可用 `docs:`、`research:`、`fix:`。尽量将同一主题的正文与索引一并提交；工具只能分步时先正文、后索引，失败时说明缺口，不能留下指向不存在文件的入口。
- 以实际文件检查日期、路径、引用、状态表述和相关差异。纯资料维护无需运行 ComfyUI、安装依赖、批量重试外部链接或建立测试／CI 体系。

## 一次归档的简短自查

- [ ] 是否回答了明确的问题，且固定平台与两个贴吧的实际覆盖可查？
- [ ] 是否保留原作者署名、原帖标题和直达链接，并区分原文内容与本库整理？
- [ ] 是否提供精确版本和实际读取范围？
- [ ] 同图实值、通用推荐、工程补值及未知项是否分开？
- [ ] 是否说明可迁移做法、适用边界及待验证内容？
- [ ] 正文已保存，索引链接有效，重复与更正已处理？
- [ ] 是否如实报告未完成、未出图与未保存的部分？

这些是文档整理提示，不是新增的实验或测试要求。
